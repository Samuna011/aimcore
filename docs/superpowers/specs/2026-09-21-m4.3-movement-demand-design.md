## Goal

Answer: **how does a sensitivity / acceleration configuration behave as movement demand changes?**

Make **configuration × movement demand → behavior** first-class in analysis and collection design. Never declare a winner. Never recommend settings. Never encode “large flicks need acceleration” as a rule.

This milestone ships:

1. Derived **MovementDemand** + **ProcessorExposure** on shots/candidates  
2. Demand-stratified / interaction-ready extensions to condition comparison  
3. A prescribed collection matrix (playbook)  
4. A dedicated controlled flick-demand ladder (`FLICK_DEMAND`) for factorial cells  

Existing tasks still contribute **continuous** demand features (hybrid breadth).

## Non-goals

- Fitted interaction models, p-values, CIs, ML  
- Recommendations / “best sens” / rankings  
- Hard-coded “large → use accel”  
- Lab UI analysis surface or matrix auto-runner  
- Retuning Raw Accel from comparison tables  
- Treating `trial_type` as the only demand axis  
- Universal permanent micro/medium/large/extreme bin edges (not yet)  
- Multi-trial pooling beyond two-trial compare (M4.2 shape)  
- Changing GRIDSHOT / TRACKING / STATIC_CLICK / FLICK_LADDER / ONE_WALL_SIX knobs

## Why this matters

A setting can look strong on micro-adjustments and weak on large turns (or the reverse). Raising **baseline sensitivity** scales all movements; **acceleration** can raise effective sensitivity mainly at high physical input speed. Those mechanisms are not equivalent. The analysis must preserve dimensions that let later work distinguish them — without assuming which is better.

```text
Configuration (sens, processor, accel params)
                 ×
        Movement demand (task/exposure features)
                 ↓
          Observed behavior
```

## Conceptual model

### MovementDemand (configuration-independent)

Describes **what the movement/task asked for / what physical motion occurred**, not how the processor transformed it.

| Field | Meaning |
|-------|---------|
| `angular_displacement_deg` | What the camera/hand path actually spanned (candidate) |
| `target_distance_deg` | Angular distance from aim onset to target (when known) |
| `commanded_yaw_deg` | Controlled task demand when stamped (ladder); `null` otherwise |
| `peak_physical_input_speed` | Peak physical raw input speed on the movement window |
| `movement_duration_ms` | Temporal extent of the candidate / acquisition |

**Rule:** Demand features must remain configuration-independent. A 60° commanded cell remains a 60° demand condition under 0.07/none, 0.09/accel, etc.

### ProcessorExposure (not demand)

| Field | Meaning |
|-------|---------|
| `peak_processed_speed` | Peak processed physical speed (or processor path peak when applicable) |
| `peak_accel_scale` | Peak stored acceleration scale on the window (`null` if absent) |

These are **exposure bridges** for explaining *how* the processor responded. They must **not** be used as demand dimensions, demand fairness keys, or stratum keys for “same movement demand.”

### Packaging in dumps

A combined convenience struct on shots/candidates is allowed (e.g. nested `movement_demand` + `processor_exposure`). Analysis code and docs must treat the split as authoritative even if serialized together.

### Buckets

Optional derived labels (`micro` / `medium` / `large` / `extreme`) may appear for tables **only after** bin edges are documented from the experimental design / ladder distributions. Continuous values remain canonical; never discard them for labels alone.

## Architecture

```text
AimTrialAnalysisBundle
        │
        ▼
  analyze_trial()
        │
        ├── reconstruct / segment / behavior / exposure (M4.1–M4.2.1)
        └── attach MovementDemand + ProcessorExposure per shot/candidate
        │
        ▼
  AnalysisResult (additive demand/exposure fields)

compare_trials(..., DemandCompareConfig?)
        │
        ├── M4.2 fairness + trial-wide deltas (unchanged semantics)
        ├── demand distribution mismatch notes (continuous)
        └── optional demand-stratum tables (e.g. commanded |yaw|)
```

### DemandCompareConfig (v1)

- `stratum`: `None` | `CommandedAbsYaw` | (later: documented displacement edges)  
- Default when omitted: attach features; report demand-distribution mismatch; **no** stratified metric tables unless requested  
- Stratum keys use **demand** fields only (never `peak_accel_scale` / processor exposure)

### Fairness

- Existing M4.2 fairness keys unchanged for trial-wide FairMatch  
- Demand-stratified views additionally require matching stratum definition (e.g. same commanded \|yaw\| cell)  
- Matching processor exposure is **not** required for a fair demand cell  

## FLICK_DEMAND (dedicated ladder)

**Purpose:** Factorial cells with controlled commanded angular demand. Distinct from `FLICK_LADDER` so `0.13.0` longitudinal rows stay comparable.

| Knob | v1 value |
|------|----------|
| Duration | 60 s active (pause-excluded) |
| Live targets | 1 |
| Radius | 0.25 (same as FLICK_LADDER) |
| Pitch | ~0° (floor-clamped) |
| Distance | STATIC_CLICK / FLICK_LADDER style |
| Commanded yaw set | `{±10, ±30, ±60, ±90}` degrees |
| Sequence | Seeded LCG; prefer no immediate repeat of same yaw |
| Spawns | Absolute world yaw from forward (−Z); camera start at 0 |
| Hit / miss | Same click semantics as FLICK_LADDER |
| Telemetry | Five-layer aim model; stamp `commanded_yaw_deg` on spawn events |

**Lobby label:** Flick Demand  
**Do not** retune `FLICK_LADDER` yaw set as a substitute.

### Hybrid breadth

| Source | Role |
|--------|------|
| `FLICK_DEMAND` | Controlled demand cells for the matrix |
| `FLICK_LADDER` | Additional large commanded yaw variety |
| `GRIDSHOT` / `ONE_WALL_SIX` / `STATIC_CLICK` | Natural continuous demand distributions |
| `TRACKING` | Continuous velocity demand (existing metric_scope rules) |

## Collection matrix (playbook)

Same milestone documents this matrix; execution is manual (no auto-runner).

| Dimension | Values |
|-----------|--------|
| DPI | Baseline **3200** (fixed) |
| Sensitivity | **0.07**, **0.09**, **0.11** |
| Acceleration | **`none`**, **`rawaccel_linear`** at one documented mid curve (snapshot processor config JSON in playbook / run notes) |
| Demand cells | commanded \|yaw\| ∈ **{10, 30, 60, 90}** via `FLICK_DEMAND` |
| Replicates | ≥1 completed `FLICK_DEMAND` run per cell; note if more |

Sign (±) is randomized / balanced by the ladder sequence; stratum key is **absolute** commanded yaw.

**Explicit non-rules:** Completing the matrix does not imply accel helps large cells. Empty or unbalanced strata → quality notes only.

Example cell grid (each cell = one sens × accel × \|yaw\| condition):

```text
                 |yaw|=10   |yaw|=30   |yaw|=60   |yaw|=90
              ─────────────────────────────────────────────
0.07 / none         ✓          ✓          ✓          ✓
0.07 / linear       ✓          ✓          ✓          ✓
0.09 / none         ✓          ✓          ✓          ✓
0.09 / linear       ✓          ✓          ✓          ✓
0.11 / none         ✓          ✓          ✓          ✓
0.11 / linear       ✓          ✓          ✓          ✓
```

(Within each run, the ladder visits all yaw magnitudes; cell-level analysis slices by commanded \|yaw\| after the fact. Full factorial of *separate* runs per single yaw is not required if one `FLICK_DEMAND` run covers the set — document which approach was used in the playbook when collecting.)

**Collection note:** Prefer **one completed `FLICK_DEMAND` run per (sens × accel)** that covers the yaw set, then stratify by commanded \|yaw\| in compare. That yields the interaction surface without 24 isolated single-angle sessions. Optional dedicated single-angle runs remain allowed for stress tests.

## Analysis outputs (interaction-ready)

Per analyzed trial:

- Continuous `MovementDemand` / `ProcessorExposure` on shots and/or candidates  
- Trial-level demand summary (quantiles of displacement, physical peak speed, duration; commanded yaw histogram when present)

Per `compare_trials` (comparison_version `"2"`):

- Existing trial-wide deltas  
- Demand-distribution mismatch notes (so unequal demand mix is visible)  
- Optional per-stratum behavior summaries (mean/median) when `DemandCompareConfig` requests strata  
- No winner language; no recommendations  

## Metric scope

`FLICK_DEMAND` uses the click-task / GRIDSHOT-like `metric_scope` profile (same as `FLICK_LADDER` / `ONE_WALL_SIX`).
