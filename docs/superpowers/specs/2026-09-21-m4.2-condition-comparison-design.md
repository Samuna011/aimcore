# M4.2 — Condition Comparison

**Date:** 2026-09-21  
**Status:** Implemented  
**Depends on:** M4.1 frozen (`analysis_version` `"1"` + [metric_scope addendum](./2026-09-21-m4.1-freeze-metric-scope-design.md))  
**comparison_version:** `"1"`  
**Packaging:** Extend `sense-analysis` (Approach 1) — pure `compare_trials` + thin SQLite loader helpers  

## Goal

Answer: **what actually changed when the controlled condition changed?**

Produce a side-by-side comparison of two analyzed trials with explicit fairness checking. Never declare a winner. Never recommend settings. Never aggregate across more than two trials in v1.

This is the foundation M4.3 needs for parameter/exposure attribution.

## Non-goals

- Recommendations / “better” / rankings
- ML, statistics (p-values, CIs), multi-trial pooling
- Lab UI or persisting comparisons to SQLite
- TRACKING re-segmentation
- Auto-picking sensitivity grids for data collection
- Coupling the comparison **engine** to SQLite

## Architecture

```text
AimTrialRecord + AnalysisResult  ×2
            │
            ▼
     compare_trials()          ← pure; no SQLite
            │
            ▼
   ConditionComparison

Optional edge:
  TelemetryDb → load → analyze_trial → compare_trials
  (loader helpers + dump_comparison example)
```

### Core API

```rust
pub fn compare_trials(
    trial_a: &AimTrialRecord,
    analysis_a: &AnalysisResult,
    trial_b: &AimTrialRecord,
    analysis_b: &AnalysisResult,
) -> ConditionComparison;
```

Preconditions (soft): `analysis_*.trial_id` should match `trial_*.id`; if not, record a quality note but still compare metrics present.

### Loader helpers (SQLite edge only)

```rust
pub fn compare_trial_ids(
    db_path: &str,
    id_a: &str,
    id_b: &str,
) -> Result<ConditionComparison, AnalysisError>;

pub fn find_comparison_candidates(
    db_path: &str,
    reference_trial_id: &str,
    criteria: CandidateCriteria,
) -> Result<Vec<AimTrialRecord>, AnalysisError>;
```

`CandidateCriteria` v1:

- Match all **fairness keys** of the reference trial
- `processor_filter`: `Any` | `MustDiffer` | `Exact { processor_id }`

Helpers may call `analyze_trial`; they must not embed comparison math.

### Example

`dump_comparison -- <id_a> <id_b>` → `comparison_<a>_vs_<b>.json` + short terminal table (factual deltas only; no winner language).

## Fairness keys

Must match for `match_status = Matched` and `comparison_validity = FairMatch`:

| Key | Source |
|-----|--------|
| `trial_type` | trial |
| `task_version` | trial |
| `task_config_json` | trial (exact string; includes configured duration / hits_required) |
| `dpi` | trial |
| `sensitivity` | trial |
| `fov_degrees_h` | trial |
| `resolution_width` / `resolution_height` / `aspect_ratio` | trial |
| `hardware_config_json` | trial (exact) |
| `view_config_json` | trial (exact) |

**Allowed to differ (intentional processor A/B):**

- `processor_id`
- `processor_version`
- `processor_config_json`

Processor differences alone never create a mismatch.

**Not a fairness key:** realized `duration_secs` / `score_secs` on the trial row (outcome timing). Configured duration lives inside `task_config_json` (e.g. GRIDSHOT/TRACKING `duration_secs`, STATIC_CLICK `hits_required`). Comparing two STATIC_CLICK finishes at 12.1s vs 14.3s remains a FairMatch if configs match.

---

## `match_status` vs `comparison_validity`

These are separate fields.

### `match_status`

- `Matched` — all fairness keys equal (processor ignored)
- `Mismatched` — one or more fairness keys differ

`condition_mismatches[]` lists every differing fairness key with `{ key, value_a, value_b }` (empty when Matched). Processor fields may appear in an optional `processor_diff` snapshot for display but are not fairness mismatches.

### `comparison_validity`

| Rule | Validity |
|------|----------|
| All fairness keys equal | `FairMatch` |
| Only `sensitivity` differs (other fairness keys equal) | `IntentionalParameterDiff` |
| Only `dpi` differs (other fairness keys equal) | `IntentionalParameterDiff` |
| Both `sensitivity` and `dpi` differ, other fairness keys equal | `IntentionalParameterDiff` |
| `trial_type` or `task_version` differs | `InvalidCrossTask` |
| Any other fairness mismatch | `OtherMismatch` |

Deltas are **always** computed when both analyses are provided. Validity annotates how to interpret the pair; it does not suppress output.

Example fair pair:

- A: 3200 DPI / 0.09 / GRIDSHOT / NoAccel  
- B: 3200 DPI / 0.09 / GRIDSHOT / RawAccel Linear  

Example intentional (still useful later):

- A: 0.09 sens vs B: 0.10 sens (same task, dpi, FOV, …)

Example invalid cross-task:

- A: GRIDSHOT vs B: TRACKING → `InvalidCrossTask` + mismatches; deltas still present for inspection

## `ConditionComparison` shape (v1)

```text
ConditionComparison
├── comparison_version: "1"
├── trial_a / trial_b: ConditionSnapshot
├── match_status
├── condition_mismatches[]
├── comparison_validity
├── processor_diff: { a, b }   // informational
├── metric_scope_a / metric_scope_b
├── metric_deltas[]            // trial-level + behavior
├── exposure_deltas[]
└── quality_summary
```

### `ConditionSnapshot`

id, trial_type, task_version, experiment_version, dpi, sensitivity, fov_degrees_h, resolution_width/height, aspect_ratio, processor_id/version, hits, shots, accuracy, score_secs, duration_secs.

### Metric entry

```text
ComparedMetric {
  name,
  a_mean, a_median,
  b_mean, b_median,
  delta_mean,      // b - a
  delta_median,    // b - a
  n_a, n_b,        // contributing shots (1 for trial-level)
  scope_hint       // from metric_scope / metric family
}
```

Nulls when `n=0` (no behavior/exposure samples) — never fake zeros.

## Metrics included

### Trial-level (from `AimTrialRecord`)

| Name | Notes |
|------|--------|
| `shot_accuracy` | hits/shots; 0 if shots==0 |
| `hits`, `shots` | counts |
| `score_secs` | TRACKING = on-target time; click = finish time |
| `on_target_ratio` | TRACKING only: score_secs/duration_secs; else null |

Trial-level: mean = median = value; `n=1`.

### Behavior (shots with `behavior` only)

Mean **and** median over that set; report `n_behavior_shots` per side.

- `endpoint_error_deg`
- `overshoot_deg`
- `correction_magnitude_deg`
- `movement_duration_ns` (JSON may also expose ms as convenience field or document /1e6)
- `path_efficiency`
- `angular_velocity_peak_deg_s`
- `jitter_rms_deg_s`

### Exposure (shots with `exposure`)

Mean **and** median; `n_exposure_shots` per side.

- raw / processed speed mean & peak (as stored on ExposureMetrics)
- `acceleration_scale` mean & peak
- `gain_ratio` mean (and peak if present)
- `cap_exposure`

### Quality summary (side-by-side, no score)

- Counts: orphan-like / no-behavior shots, multi-shot flags, selected trial flags
- Recon: max step, max speed, discontinuity count, yaw wrap crossings

---

## Aggregation rules

- **No** cross-trial pooling in v1 (exactly two trials).
- Behavior/exposure aggregates skip shots lacking that namespace.
- Prefer documenting TRACKING high orphan rates via `metric_scope` + quality_summary rather than inventing TRACKING-only metrics here.
